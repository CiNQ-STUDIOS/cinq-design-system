# CiNQ design system

Version 2.0.0. The canonical, multi-platform design system for every CiNQ product: cinqstudios.com, CiNQ RMS, Dentisto, Qeemat, and client work. It is written to be applied by AI coding agents and by people, and it cannot be applied by swapping variables: the layout grammar, the archetypes, the states and the motion are the system as much as the colours are.

The name is `CiNQ`. Not Cinq, not CINQ.

## Philosophy

Vermilion ink on a warm dark page. One near-black canvas, bone type, a single accent, big confident display type on the public site, and tools that read as instruments: one thing dominant, everything else subordinate, nothing decorated. Motion explains a change of place and then gets out of the way; in operational views it barely exists. Surfaces are objects with an edge, not glowing panels. When two agents argue about a choice, the quieter option wins.

## Principles (falsifiable, from `audit/BRAND_DNA.md` §9)

P1 one accent, one light · P2 gradients are alpha, not hue · P3 surfaces are objects · P4 glass is chrome · P5 one thing reads first · P6 motion is scroll or state, never both · P7 decks, not lists, on a phone · P8 sentence case, said plainly.

## Signature moves (`audit/BRAND_DNA.md` §10)

SM1 the five-segment C · SM2 the double bezel · SM3 the illuminated border · SM4 vermilion colour blocks · SM5 ink-veil recession · SM6 masked line reveals · SM7 ambient vermilion, one per viewport · SM8 weight as motion · SM9 grain and duotone · SM10 the pill and the disc · SM11 kicker · headline · lead · SM12 alternating section families.

Every rule in this repository traces to one of these; the trace is stated at the top of each specification.

## What makes it a system and not a theme

1. **Anti-bento grammar** (`layout-architecture/anti-bento-grammar.md`): nine testable rules about dominance, region count, weight ratio, focal element, reading path and when cards are allowed.
2. **Nine archetypes** (`layout-architecture/archetypes.md`) with wireframes, region roles, density, gradient and motion budgets and five lifecycle states each; every screen type mapped (`screen-inventory.md`).
3. **Named transitions** (`foundations/transitions-and-choreography.md`): nothing animates without a name, an anatomy, a reduced-motion behaviour and a platform mapping.
4. **Global states** (`components/global-states.md`): idle, loading, empty, error, success are specified with copy, not left to the framework.
5. **Enforcement** (`tooling/`, `AGENT_RULES.md`): lint, audit score, contrast, motion, gradient and coverage checks that fail the build; a reskin test that a token-only migration cannot pass.

## Commands

```
npm install
npm run build          tokens → implementations, showcase pages, contrast matrix, coverage matrix
npm run verify         tokens:check · contrast · motion:check · coverage · typecheck
npm run lint           ESLint with the cinq rule on code/ and showcase/
npm run audit -- <dir> --report audit.md     score a product
```

## Using it in a product

`scripts/install-to-product.sh <path> --submodule` vendors this repository at `brand/design-system/`. Then tell the agent: "Read brand/design-system/AGENT_RULES.md first. This is a [Next.js / Flutter] product; its primary surface is a [console / dashboard / mobile utility]. Fill project-profile.md, install the tokens, then build [the screens] on their archetypes and walk the checklist." For tools without file access, paste `prompts/standalone-system-prompt.md`.
